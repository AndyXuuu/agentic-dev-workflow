# Agentic Development Workflow 使用手册

> 面向 AI Coding Agent 的项目无关软件工程治理与交付框架。

本手册用于解释和示例，不是第二套规范源。强制行为以当前仓库 `AGENTS.md` 和被明确调用的
Skill 为准；本手册与其不一致时应修正本手册，不能用示例覆盖权威规则。

## 一、核心原则

不要让 Agent 在风险未分类时直接进入写代码模式。明确、局部、低风险的小改动使用
`AGENTS.md` 定义的 Fast Path；不满足全部条件时再进入标准流程。

标准流程是：

```text
需求分析 -> 架构设计 -> 开发实现 -> 业务验收 -> 交付 Review
```

明确、局部且不改变验收、Owner、契约、数据、权限、迁移或交付风险的变化可以直接吸收；
material 需求或架构变化才暂停一次，说明差异、影响和修订计划。完整规则以 `AGENTS.md`
为唯一权威来源。

### Fast Path

文档、格式、注释、非敏感本地配置，以及验收明确且局限于现有 Owner 的小改动，在不涉及
契约、数据、权限、安全、依赖、生成、部署或跨模块边界时执行：

```text
确认 Owner 和最小范围 -> 修改 -> 最小相关验收 -> 简短交付
```

Fast Path 在加载可选生命周期或工程领域 Skill 前判定，不因文件属于前端或后端就自动加载
`$ax-dev`、`$ax-frontend` 或 `$ax-backend`。它不生成 PRD 或完整设计报告，也不默认执行无关
的全量项目门禁。详细准入和升级条件以 `AGENTS.md` 为唯一权威来源。

### 决策协作模型

| 参与者 | 负责内容 |
|---|---|
| 用户 | 目标、业务优先级、审美偏好、风险取舍、明确约束和最终决策 |
| Agent | 调查当前事实、区分现状与意图、评估方案与代价、实施并验证结果 |

Agent 不把用户提出的技术原因或修改办法直接翻译成代码。先检查真实页面、配置、契约和
Owner，再选择保持现状、局部修正或采用该方案。

改进已有实现时，先记录与目标相关的基线和成功信号，修改后使用同一信号比较。业务验收
只说明已保护的契约仍成立，不能单独证明结构、性能、可用性或视觉效果变得更好。

假设只能是短生命周期的工作假说。当它开始影响实现、验收预期、权威文档、归档或交付时，
必须用源码、配置、运行状态或合同证实，由用户明确决定为目标/约束，或退出并清理依赖它的
计划与文档。非阻断未知只能作为证据缺口保留。

功能需求、流程和验收标准之前，建立紧凑的术语/对象注册表。只登记会影响行为的参与者、
实体、动作、事件、状态和外部概念；普通字段、助手、局部状态和标准技术术语不提升为全局
概念。详细阈值以 `AGENTS.md` 为唯一权威来源。

## 二、全局与项目边界

```text
全局 AGENTS      -> 项目无关的工程门禁与安全规则
生命周期 Skill   -> 需求、架构、开发、Review 阶段
工程领域 Skill   -> 可迁移的前端、后端与结构质量规范
仓库操作 Skill   -> Git 操作和项目接入流程
外部集成 Skill   -> TAPD 等外部工具的访问流程
项目 AGENTS      -> 项目技术栈、命令、强约束、权威来源和独立运行的最小门禁
项目适配 Skill   -> 把全局流程导航到项目 Owner，不复制全局规范
```

全局规则和 Skills 禁止写入具体项目路径、框架选择、接口地址、部署拓扑或业务规则。跨仓
契约必须明确唯一源契约，生成投影、同步副本和消费者客户端保持派生关系。

## 三、模型分工

| 角色 | 模型 | 用途 |
|---|---|---|
| 架构 / Review | `gpt-5.6-sol` | 高风险判断、架构设计、最终审查 |
| 开发 | `gpt-5.6-terra` | 日常实现、普通 Bug、重构落地 |
| 快速处理 / 文档 | `gpt-5.6-luna` | 重复性工作、文档和清理 |

配置文件：

```text
~/.codex/arch.config.toml    -> gpt-5.6-sol
~/.codex/dev.config.toml     -> gpt-5.6-terra
~/.codex/review.config.toml  -> gpt-5.6-sol
```

## 四、Skill 分类

| 模块 | Skill | 菜单说明 |
|---|---|---|
| `lifecycle` | `$ax-pipeline` | 全流程：需求、架构、开发、业务验收、交付 |
| `lifecycle` | `$ax-prd` | 需求范围、用户流程和验收标准 |
| `lifecycle` | `$ax-arch` | 模块边界、数据流、接口、迁移和恢复 |
| `lifecycle` | `$ax-dev` | 按已确认需求和设计实施代码 |
| `lifecycle` | `$ax-review` | 交付前检查需求、架构、验收证据、风险和回滚 |
| `disciplines` | `$ax-frontend` | 前端 Owner、状态、设计系统、响应式和可访问性 |
| `disciplines` | `$ax-backend` | API、领域边界、数据一致性、并发、安全和迁移 |
| `disciplines` | `$ax-structure-review` | 职责边界、依赖方向、重复逻辑、抽象和复杂度 |
| `disciplines` | `$agent-workflow-measurement` | 只读分析 Agent、OMP 与 Orca 会话耗时和工具开销 |
| `repository` | `$git-workflow` | 安全执行本地提交、远程同步和冲突停机 |
| `repository` | `$ax-sdd` | 定位一个 Domain 的当前 why/what/how/proof 闭包 |
| `repository` | `$ax-project-bootstrap` | 选择并完整复制已登记脚手架 |
| `repository` | `$ax-project-adapter` | 根据项目事实生成精简适配 Skill |
| `integrations` | `$tapd-query` | 只读查询 TAPD 需求和缺陷 |

## 五、安装和刷新

```bash
$HOME/Documents/codex/agentic-dev-workflow/bin/install.sh
```

安装脚本根据 `skills/catalog.tsv` 创建 Skill 软链接，并链接 `arch`、`dev`、`review` 三个
Profile 和 `~/.codex/AGENTS.agentic-dev-workflow.md`。它不会覆盖 `~/.codex/AGENTS.md`。

安装前会运行 `bin/validate-skills.sh` 和 `bin/validate-scaffolds.sh` 的结构模式，检查目录、
Skill 元数据和脚手架注册表。要使本仓库规则成为活动全局规则，运行：

```bash
$HOME/Documents/codex/agentic-dev-workflow/bin/apply-global-agent.sh
```

`bin/uninstall.sh` 只删除本仓库创建的链接，保留无关的全局规则和备份文件。

## 六、Domain SDD

当项目明确采用 Domain SDD 时，使用 `$ax-sdd` 维护项目全部 current behavior；Domain 是稳定的组织、Owner 和导航单位，不是项目规范覆盖范围。按任务从 `sdd/index/domains.json` 选择 primary/affected Domain，并读取最小充分上下文闭包；这只控制上下文加载预算，不代表项目只定义该 Domain：

- 从 `sdd/index/domains.json` 选择 primary Domain，并仅在其拥有的行为合同确实变化时登记 affected Domain；
- 读取命中 Domain 的 Metadata、PRD、SPEC、Logic Flow、业务 Test Flow、Dictionary、直接技术依赖、Requirement 和 Acceptance Boundary；
- 直接更新 canonical Artifact，并保持 traceability 与 projection 一致；
- 使用项目已有的 SDD 检查入口，不在全局层创建第二套工具。

业务 Test Flow 和 Acceptance Oracle 是业务契约，不是全局代码测试 Skill。它们必须从已接受
的 Spec/Requirement 产生，并以可观察业务结果为验收依据。源代码和运行证据仍是实现/证据，
不能用文档检查代替行为验收。

## 七、推荐工作流

### 新建项目或应用包

```text
$ax-project-bootstrap 选择已登记脚手架并完整生成到目标目录
$ax-project-adapter 根据生成结果校准项目 Owner 和入口
$ax-pipeline 从实际 Owner 规划和实现业务改动
```

目标目录已存在时不得覆盖或手工拼接脚手架；按迁移或架构任务处理。

### 新功能

```text
$ax-pipeline 需求：用户钱包冻结余额。请先给需求、架构、实现范围、业务验收和交付检查。
```

如果需求已清楚，可以分阶段，但仍只有一个 primary workflow：

```text
$ax-prd -> $ax-arch -> $ax-dev + 按需组合 $ax-frontend / $ax-backend
        -> 使用已接受 Spec/Test Flow 的业务验收证据
        -> $ax-review（仅在交付边界需要时）
```

### Bug 修复

```text
$ax-pipeline Bug：连续点击充值按钮生成多笔订单。请先说明复现、业务影响、最小修复和验收证据。
```

先保留能证明 Bug 的修复前失败证据，修复后重复同一条可观察业务证据。是否维护自动化
检查由项目自己的契约和发布门禁决定；全局工作流不因形式要求创建测试套件。

### 只做开发

```text
$ax-dev 根据已确认的 DESIGN.md 实现冻结余额接口，开始前说明 Owner、复用模块和最小验收路径。
```

### 交付前检查

```text
$ax-review 检查本次改动的需求匹配、架构风险、业务验收证据、上线风险和回滚方案。
```

## 八、需求、架构和范围变化

如果开发中发生 material 需求变化，暂停当前依赖路径，说明：

1. 需求或设计差异；
2. 变化后的验收标准与受影响 Owner、契约、数据、权限、迁移和风险；
3. 已有计划、文档和代码哪些继续有效，哪些需要修改或清理；
4. 修订后的下一步，以及仍需用户决定的事项。

如果发现原设计不合理，先用已验证的现状和成功信号说明原因，再比较最小替代方案、迁移、
恢复和验收路径。不要把未解决的 material 假设写入契约、数据模型或 canonical 文档。

## 九、质量红线

以下情况不应直接进入开发：

- 非 Fast Path 需求没有可观察验收标准；
- 影响数据模型但没有迁移和恢复方案；
- 影响支付、钱包、权限或计费但没有风险分析；
- 没有搜索已有类似逻辑；
- 同一业务规则准备复制到多个 Owner；
- Bug 修复没有修复前后同一条失败证据；
- 把实现细节、文档检查或静态结果冒充业务行为通过。

## 十、常用操作

对于 OMP `conversation.questionFirst` 能力，使用可选运行时适配器：

```text
$omp-question-first 检查兼容性并安装可回滚启动器。
```

对于本地提交和远程同步使用 `$git-workflow`；对于 TAPD 只读查询使用 `$tapd-query`。不要
在全局 Skill 中写入项目路径、凭证、业务规则或项目专属命令。
