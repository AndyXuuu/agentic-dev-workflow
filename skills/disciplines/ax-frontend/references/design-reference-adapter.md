# 外部设计参考适配

适用于 Figma、截图、TypeUI、designmd.ai、designmd.co、awesome-design-md、Google DESIGN.md 或其他品牌规范。

## 职责分离

- 项目规则文件定义工程约束和交付要求。
- 项目设计系统定义真实 Token、组件、资产和视觉行为。
- 本 Skill 定义 Agent 如何发现、转换、实现和验证。
- 外部行业规范用于校准可用性、行为和质量原则，不自动成为项目视觉 Owner。

## 决策优先级

发生冲突时按以下顺序处理，并明确记录无法同时满足的约束：

1. 适用法律、WCAG 等无障碍基线与目标平台硬约束。
2. 项目已确认的业务流程、用户风险、设计系统和品牌契约。
3. Material Design、Ant Design、Apple HIG、Fluent 等外部行业参考。

只吸收与目标平台适用的原则、语义和行为契约。不要复制外部体系的固定间距、字号、圆角、颜色、阴影、品牌外观或平台专属组件；也不要为同时容纳多个体系而制造无真实消费者的通用抽象。

## 转换步骤

1. 确认来源、版本、目标页面、允许影响的组件和必须保持的业务流程。
2. 提取视觉意图：氛围、层级、密度、排版关系、色彩角色、间距节奏、形状、深度、组件行为、响应式、Motion、Do/Don't。
3. 盘点项目现有 Token、组件、变体、资产和交互契约。
4. 建立映射表：外部意图 → 项目语义 Token/组件；不要建立外部十六进制 → 新硬编码值的机械映射。
5. 标出缺口和冲突：无对应 Token、组件状态不足、字体/资产授权、可访问性、业务流程、共享组件影响范围。
6. 只对已确认缺口提出最小扩展；新 Token 必须可复用，新变体必须有清晰组件 owner。
7. 实现后同时验证视觉意图、项目一致性、业务行为和可访问性；主题或组件被定制后重新验证实际结果，不继承来源体系的合规假设。

## 必须拒绝或暂停的情况

- 用户要求“直接套用”，但没有提供可读取的参考文件、节点、截图或 URL。
- 外部品牌色、字体、Logo、照片或商标资产的授权不明确。
- 参考要求会覆盖项目的权限、支付、数据、导航或状态契约。
- 改共享组件会影响未授权页面或流程。
- 项目设计系统与外部规范冲突且权威来源未确认。
- 仅凭文本参考要求承诺像素级复刻，但缺少视觉验证条件。

## DESIGN.md 使用原则

- 有结构化 Token 时读取精确值与引用关系，同时读取 prose 中的用途和理由。
- 兼容 legacy 文件时明确标注未验证字段和缺失状态，不假设符合当前规范。
- 若项目已有 DESIGN.md，优先更新现有 canonical file；不要创建第二份冲突文件。
- 若存在官方 linter/exporter，先验证再消费；未知 section 可以保留，但不能绕过项目约束。
- 最终代码使用项目设计系统的真实 Token 和组件名称，而不是外部文档的品牌命名。

## 交付说明

报告：

- 保留了哪些设计意图
- 映射到哪些现有 Token/组件
- 丢弃或替换了哪些外部品牌元素
- 新增了哪些可复用 Token/变体及其 owner
- 哪些视觉差异仍需截图、Figma 或人工确认
