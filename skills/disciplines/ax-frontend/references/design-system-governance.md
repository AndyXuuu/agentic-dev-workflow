# 设计系统治理与采用检查

适用于设计系统、Token、主题、共享 UI 组件、全局样式的建设与审查，以及设计标准与生产页面表现不一致的诊断。目标是建立可追踪、可执行的正确做法，不以单个页面或工具作为默认答案。

## 0. 固定审计快照

审查/诊断默认只读：

1. 开始时记录仓库路径、当前分支、HEAD、工作树状态和审查时间；区分已提交基线与含未提交改动的当前快照。
2. 先读取脚本再决定是否执行。会写报告、缓存、快照、生成源码或构建产物的 lint、build、preview 命令不属于只读检查；未获得修改授权时只检查其配置和已有产物。
3. 优先使用 `rg`、`rg --files`、源码解析、Git 只读命令和不会落盘的项目原生命令。不要为完成审查修改配置、更新 baseline 或清理工作树。
4. 已有报告只有同时具备生成时间、输入范围、规则版本或源码版本等新鲜度证据时，才能证明当前快照；否则只作为历史证据。
5. 结束时重新记录 HEAD 与工作树状态。审查期间发生变化时，标出受影响证据并重新验证；无法重验则将结论限定到原始快照。

## 1. 确认适用性与成熟度

先确认目标平台、产品约定、设计系统覆盖范围和真实消费者，再选择治理强度。行业规范用于校准原则和行为，不直接成为项目视觉 Owner；优先遵循法律与无障碍要求、目标平台约定和项目已确认的业务/设计契约。不要复制 Material、Ant Design、Apple 等体系的品牌颜色、固定尺寸、组件外观或平台专属交互。

按当前事实选择最小充分治理：

| 形态 | 最小治理 | 按需增加 |
| --- | --- | --- |
| 单应用或少量局部组件 | 唯一 Token/样式 Owner、真实组件复用、关键流程行为与无障碍验证 | 轻量组件展示、局部契约验收 |
| 稳定共享组件库 | 公开入口与 Owner 清单、真实组件示例、相关状态契约、消费者回归 | 视觉回归、变更说明、废弃提示 |
| 跨团队、跨包或独立发布体系 | 版本与兼容策略、迁移指南、废弃周期、消费方影响追踪 | 自动发布门禁、跨仓库契约验证 |

不要为了“像一个设计系统”而默认引入 Storybook、三层 Token、全量截图矩阵、独立发包或复杂版本流程。只有消费者规模、稳定契约或回归风险能证明收益时才启用；当范围收缩时也允许简化。

确认当前采用模式及责任边界：

- **直接复用**：使用已有 Token、组件和行为契约，不在调用方覆盖内部规则。
- **扩展现有体系**：通过正式 Token、variant、slot 或组合接口补齐可复用能力，并验证原有消费者。
- **替换子系统**：明确被替换 Owner、迁移范围、兼容期和回滚路径，避免新旧规则长期并存。
- **完全自定义**：仅在平台、品牌或产品需求无法由现有体系满足时采用；自定义后重新验证全部实际暴露的状态、对比度、焦点、键盘、目标尺寸和响应式行为，不能沿用基础组件库“已合规”的假设。

## 2. 建立设计契约

先定位并记录四类 Owner：

| 契约层 | 内容 | 正确标准 |
| --- | --- | --- |
| Foundation | 色彩、排版、间距、圆角、阴影、层级、Motion、断点、资产 | 有唯一源码、明确语义、主题完整、引用可解析 |
| Component | 原子组件、业务共享组件、variant、交互与可访问性契约 | 真实组件实现拥有样式和行为，调用方不复制内部规则 |
| Catalog | Design page、Storybook、文档或设计库 | 直接渲染真实组件并展示受支持契约，不维护平行实现 |
| Consumer | 页面、场景组件和产品流程 | 使用已批准的 Token、组件、variant 和资产入口 |

为每层确认 canonical source、变更 Owner、同步方式和验证命令。同一信息只保留一个定义源；其他层通过引用、导入、生成或验收与其保持一致。

## 3. 规范设计系统本身

### Token

- 可采用 `primitive → semantic → component` 分层，也可遵循项目已有层级；每个公开 Token 必须表达稳定用途。全局/共享 Token 需要跨组件或跨场景语义，组件私有 Token 只需拥有稳定的组件内部语义。
- 检查未定义引用、循环引用、重复含义、同名异义、无消费者 Token，以及各支持主题中的缺失值。
- 对每个疑似未定义引用先分类来源：项目源码、框架/组件库默认值、运行时注入、生成文件、环境配置或声明内 fallback。只有在目标执行路径上应存在、没有可解析来源且没有有效 fallback 时，才报告为已确认缺失；其余标记为待运行时验证。
- 对别名和主题覆盖追踪最终引用链；静态检查无法证明计算值时，通过浏览器计算样式或业务验收补证，不把搜索不到项目内定义直接等同于缺失。
- 页面或功能专属数值留在明确的场景 Owner；只有具备跨场景语义时才提升为全局 Token。
- Catalog 展示 Token 的真实名称、计算结果、用途和限制；展示数据、分组、数量说明和状态元数据优先从权威清单生成，无法生成时由一致性检查约束，不能只校验 Token 名称存在。

### 组件

- 共享组件集中拥有 DOM 语义、基础视觉、variant、尺寸、状态、焦点、键盘和 ARIA 契约。
- Catalog 存在时直接导入真实组件，只覆盖组件契约实际暴露且与风险相关的 variant、size、交互状态和内容边界；不要机械构造组件并不支持的全量状态矩阵。
- 数据型组件按实际契约与风险覆盖 Loading/Skeleton、Data、Empty、Error；Overlay 组件覆盖其支持的打开、关闭、居中或锚定位置、所属视口/包含块内的完整包含、安全边距、Backdrop、层级、滚动、焦点捕获与恢复；嵌入场景区分 Widget/iframe 与顶层宿主边界。浏览器验证必须真实展开 Overlay 并检查最终计算布局，不能只检查触发器、DOM 存在或打开命令回执。
- 覆盖项目支持的主题、最窄视口、关键断点、Reduced Motion 和高对比度模式。
- Catalog 无需机械展示内部 Helper 或专用骨架。稳定共享契约应有可追踪的真实示例、业务契约验收或明确豁免；单应用局部组件只需与其风险匹配的验证。
- 不按目录中的文件数量推断公开组件。对稳定共享库，根据公开 export、稳定 import 入口、项目文档和真实消费者建立清单，再记录 Owner 与最小验证入口。豁免可用于内部 Helper、专用场景实现、生成/声明式内容或其他明确原因。

### 平台约定、空间与反馈

- 优先使用目标平台和产品中已建立的导航、选择、编辑、确认与返回约定；创新交互需要可发现性、可访问性和用户价值证据。
- 用对齐、邻近、层级和留白表达关系；控件靠近其影响的内容，主要任务直接可见，低频次要工具按需呈现。不要把固定栅格或间距数值从外部规范照搬进项目。
- 反馈强度与风险、等待时间和恢复成本匹配：字段错误就地关联，可见结果不重复弹 Toast，长任务提供状态并在可取消时提供取消，Dialog 只用于重要、可行动且确需阻断的反馈。
- 修改主题、组件样式或交互后，重新验证实际暴露的对比度、焦点、目标尺寸、状态辨识和行为；底层组件库的原始合规结论不能自动继承到定制结果。

### 全局样式

- 全局层只拥有 reset、基础元素、主题接线和真正跨场景的组件规则。
- 检查 reset、normalize、utility layer 和组件库基础样式是否移除了仍被组件依赖的浏览器默认行为；需要覆盖时显式恢复定位、焦点、表单、媒体或 Overlay 契约，不假设原生默认值在 Reset 后仍存在。
- 按选择器、依赖 Token 和消费者审查大文件；发现多个业务领域、覆盖链或高频 `!important` 时，确认样式归属和级联契约。
- 不以拆文件或行数作为完成标准；以单一 Owner、依赖方向、变更局部性和可验证性判断结构。

## 4. 检查生产采用

先检查所有共享 Foundation、Component 和 Catalog Owner，再选择生产消费者。小型项目检查全部主要页面；大型项目在用户未指定全量审计时，至少选择三个不同场景，并满足：包含最高业务/安全风险流程、一个高交互或 Overlay 场景、一个具有远端数据状态和响应式差异的场景。每个受影响的主要领域至少覆盖一个消费者；无法覆盖时明确列入未验证范围。

建立追踪矩阵：

| 页面/场景 | 使用的共享组件 | 使用的语义 Token/资产 | 局部实现及理由 | 状态/主题/视口证据 |
| --- | --- | --- | --- | --- |

逐项检查：

1. 从页面追踪到场景组件，再追踪到共享组件和 Token Owner。
2. 确认相同视觉或交互语义复用同一组件/variant，不在调用点复制组件内部规则。
3. 确认 Token 按声明用途消费；“使用了命名 Token”不能单独证明语义正确。
4. 允许原生元素和局部样式，但必须符合语义 HTML，并说明共享抽象为何不适用。
5. 检查页面状态、主题、响应式、内容膨胀、键盘与焦点，不用静态默认态代表完整采用。
6. 分别记录设计契约缺口和采用缺口；生产页面不得被迫复制设计系统缺失的能力。
7. 记录抽样理由、覆盖领域和停止条件；发现跨领域重复或共享契约缺陷时扩大到所有直接消费者，直到影响边界明确。

## 5. 建立自动化检查

按项目能力选择最小充分组合：

- Token 完整性：解析未定义/循环引用、主题缺值、重复定义和公开 Token 清单漂移。
- Catalog 一致性：适用于稳定共享契约；核对公开组件和展示/豁免清单，验证展示直接使用真实 Owner。
- 组件业务契约验收：验证 variant、状态、DOM 语义、键盘、焦点和 ARIA。
- 静态采用检查：检查禁止的 raw/arbitrary value、绕过资产入口、受控组件的平行实现和受限 Token 用途。
- 视觉回归：只在视觉契约稳定且回归风险值得维护成本时，对相关共享组件状态和代表性页面建立截图基线；控制字体、数据、动画、时间和视口以降低噪声。
- 浏览器验证：在支持主题和关键视口检查计算样式、交互、控制台与可访问性树。主题、字体或动效会影响取样时，等待加载与过渡稳定或重新加载后再测量，并确认当前主题和焦点状态；不得把 transition 中间帧当作最终对比度或布局结论。

版本、迁移和废弃门禁只用于跨团队、跨包、独立发布或存在兼容承诺的共享体系；单应用内部重构不应被迫模拟公共库发布流程。

通用扫描不得静默排除设计系统 Owner。确需排除生成文件、展示夹具或原始 Token 值时，为该范围配置专用检查，并在配置中记录原因和替代验证入口。

## 6. 审查输出

先给结论，再分别报告：

1. 设计契约：Token、组件、Catalog 是否完整且一致。
2. 生产采用：代表性页面是否按语义复用，局部实现是否合理。
3. 自动化：哪些结论由静态检查、视觉证据或浏览器验收持续保护。
4. 审计快照：分支、HEAD、工作树状态、审查期间是否变化，以及已有报告的新鲜度。
5. 抽样范围：选择理由、已覆盖领域、停止条件和未覆盖消费者。
6. 未验证范围：缺失环境、数据、主题、视口或人工视觉确认。
7. 最小改进：优先修复权威 Owner 和验证链，再处理消费者；不通过复制规则维持表面一致。
