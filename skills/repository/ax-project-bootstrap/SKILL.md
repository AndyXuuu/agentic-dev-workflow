# Project Bootstrap

把已验证脚手架当作新项目的完整起点，不从空目录重新发明同类框架。只负责建立基线；业务需求、项目架构、迁移和功能实现由生成后的项目规则及对应生命周期 Skill 负责。

## 1. 确认 Bootstrap 合同

写入前只确认会影响脚手架选择的事实：

- 目标目录和它所属的 Git 仓库；读取父仓库适用的 `AGENTS.md` 并检查工作树。
- 目标是全新项目、新应用包还是已有项目迁移。
- 应用类型、必须固定的框架/包管理器、部署形态和浏览器/服务边界。
- 脚手架声明的依赖、许可证和安全前提是否适用。

目标必须不存在；已有空目录也按生成器合同处理，不绕过覆盖保护。若用户要求把脚手架合入已有非空目录，停止本流程，改为迁移/架构任务，不做文件级拼接。

## 2. 发现并选择已注册脚手架

从本 Skill 的真实目录向上三级定位工作流根目录，读取 `scaffolds/catalog.tsv`，只在登记项中选择，不扫描相邻目录或凭名称猜测未注册框架。选中后完整读取 catalog 指向的说明和脚手架 `AGENTS.md`。

按应用类型、技术栈硬约束、认证/API 边界、部署要求和许可证选择。存在一个兼容脚手架时优先复用；存在多个实质不同的兼容项时说明差异并让用户选择。没有兼容项时记录缺口并转入 `ax-arch`，不得静默自行重建一个与现有脚手架同类的框架。

视觉品牌、业务接口和产品文案通常属于生成后的适配工作，不是拒绝结构兼容脚手架的理由。框架、运行时、包管理器、许可证或安全模型冲突才属于实质不兼容。

## 3. 完整生成基线

使用 catalog 登记的官方生成器，不手工 `cp`，也不挑选部分目录。生成结果必须完整保留脚手架提供的：

- 源码、依赖清单、锁文件和构建配置；
- `AGENTS.md`、设计契约、项目 Adapter、Owner 地图和说明文档；
- API/数据示例边界、验证脚本及其配置。

运行前说明目标路径、将下载/安装的依赖和临时磁盘影响。生成器必须在临时目录完成验证、失败清理和原子交付；若它不满足该合同，先修复脚手架生成器，不把风险转移给目标项目。

生成失败时保留命令和错误证据。不要把临时或部分结果改名成交付目录，也不要绕过失败检查继续规划。

## 4. 以生成结果规划项目工作流

生成成功后，先读取复制后的 `AGENTS.md`、设计契约和仓库内 Adapter，再以这些实际文件作为 Owner 基线：

1. 记录生成提交/工作树边界，确认组织文件和验证入口完整存在。
2. 把脚手架的成功验证作为当前未修改基线；输入未变化时不立即重复相同聚合门禁。
3. 使用 `ax-project-adapter` 更新复制后的薄适配层，只替换项目事实和导航，不先删掉再重建。
4. 再使用 `ax-prd`、`ax-arch` 或 `ax-pipeline` 规划业务能力、认证/API 接入和必要的框架差异。
5. 按最小纵向切片逐步替换 Demo/Mock；在真实替代 Owner 和验证存在前，不提前删除脚手架契约。

设计系统的 Token、共享组件、Catalog 和生产消费者是一组契约。品牌适配应修改其权威 Owner，不得只复制页面外观或把 Catalog/静态门禁作为“演示文件”删除。

## 5. 验证与交付

- 确认目标此前不存在，最终目录只在生成验证成功后出现。
- 确认 catalog、说明、生成器和脚手架源目录均来自同一工作流版本。
- 检查生成结果能脱离个人全局 Skill 读取自身规则并找到 build、lint、业务验收和设计契约入口。
- 报告选用脚手架、兼容性依据、生成目标、生成器验证结果和后续项目适配范围。
- 若未采用已登记的兼容脚手架，必须给出可验证的不兼容依据；“从头写更快”不是依据。

回滚只删除本次新生成且此前不存在的精确目标目录；删除前仍需遵守当前环境的破坏性操作审批规则。
